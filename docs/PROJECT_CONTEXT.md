# Project Context

## 1. Project Objective & Summary
- **Goal**: Develop and evaluate **MobilisTransit** (originally titled *MobisTransit* in `tema.MD`), an integrated multidisciplinary system for a Master's in Computer Engineering project (Group D6 — João Carreira & Lourenço Ferreira, ESTG / University of Leiria and Oeste, 2026/2027) that simulates an urban bus line in Leiria (**Mobilis Line 9**), predicts downstream bus arrival times using machine learning, enables controlled delay-propagation experiments, and presents synchronized arrival and delay insights across an Android mobile app (2D and AR) and a web administration interface with a tool-restricted conversational assistant.
- **Domain & Target Users**:
  - **Domain**: Public urban bus transit operations, microscopic traffic simulation (Eclipse SUMO), supervised bus arrival-time regression, mobile augmented reality (ARCore), and agentic scenario analysis (LangGraph + Ollama).
  - **Target Users**:
    1. **Students and mobility analysts** (primary evaluation users of the first version): configure and execute paired delay scenarios (baseline vs. perturbed runs), analyze downstream delay propagation, and compare 2D vs. AR visualizations via laptop/web administration and Android phone.
    2. **Everyday bus passengers** (represented through arrival-query user flows): consult upcoming bus arrivals, predicted delays relative to published timetables, favourite stops, and stop-level AR panels.
- **Scope Summary**:
  - Single-route prototype centred on **Mobilis Line 9** (using the **existing Line 9 SUMO model** already created by the team, confirmed by user in `DEC-004`), operating on **SUMO simulated and recorded journeys** without assuming live Mobilis GPS telemetry or ticketing data.
  - Integrates four Master's course units (UCs) sharing a single canonical state, prediction, and experiment-ID contract:
    - **TEI** (*Tecnologias Emergentes e Inteligentes* / EIT): Central backend REST/JSON API, source adapter, SUMO/TraCI simulation worker control (supporting stop holds and traffic multipliers), historical store, administration web forms, and LangGraph/Ollama 3-tool scenario analysis assistant.
    - **AAP** (*Aprendizagem Automática e Profunda*): Multi-scenario journey dataset generation from SUMO logs, strictly causal feature engineering, leakage-free training/evaluation comparing a historical segment-average baseline, regularized linear regression, and XGBoost, and publishing one versioned regression model artifact.
    - **DDM** (*Desenvolvimento para Dispositivos Móveis*): Native Android (Kotlin) application providing 2D route tracking (E1), stop arrival details (E2), saved delay scenario execution and comparison (E3–E4), persistent favourites (E6), local caching, synchronized updates, and an offline bundled demonstration player.
    - **RVA** (*Realidade Virtual e Aumentada* / VAR): Stop-anchored AR arrival panel paired with a **compact 3D mini-route** (via printed reference images, E5), **Tabletop 3D full-route AR mode** (via horizontal plane detection for desk/classroom inspection, confirmed per `main_changes7.tex` in `DEC-001`), synchronized with the 2D state, plus a within-subjects 2D vs. AR usability evaluation. VR and TEI business model are confirmed out of scope (`DEC-001`).

## 5. Constraints & Open Technical Choices
- **Mandatory Constraints**:
  - **Mobile Platform**: Native Android developed in **Kotlin** (`MobilisTransit_DDM_Draft/README.md`, `main.tex` §3; `main_changes7.tex` §3.2; `apresentação.md` Slide 8).
  - **Traffic Simulator**: **Eclipse SUMO** controlled via **Python and TraCI** (`main_changes7.tex` §3.1, §4.2; `apresentação.md` Slide 5, Slide 7).
  - **Server-Side Compute & API Protocol**: Simulation execution, ML inference (Python server + relational database), and agent orchestration execute centrally on the project server; clients consume a shared **REST/JSON** contract carrying journey, scenario, sequence, simulation clock, generation time, and model version metadata (`MobilisTransit_DDM_Draft/main.tex` §1, §3.1, §4; `main_changes7.tex` §3.1, §4.2; `apresentação.md` Slide 5, Part 3B).
  - **Agent Orchestration**: **LangGraph** state graph with local open-weight tool-calling LLM via **Ollama** (external API or lighter/separate model execution permitted as hardware contingency) (`main_changes7.tex` §2.4, §3.3, §6; `apresentação.md` Slide 10, Slide 12).
  - **AR Platform & Tracking Constraints**: **ARCore** configured as `AR Optional` using `Augmented Images` on printed stop reference markers and **horizontal plane detection** for Tabletop mode in controlled indoor settings (no generic street-sign recognition; mandatory 2D fallback) (`MobilisTransit_DDM_Draft/main.tex` §3.1, §5.4; `main_changes7.tex` §3.2, §4.4, §6; `DEC-001`).
  - **Offline / No-External-Map Operation**: Initial Android version draws its own 2D schematic route diagram without external mapping SDKs, and supports offline viewing of cached data and a bundled demonstration trip (`MobilisTransit_DDM_Draft/main.tex` §4).
  - **Data & Privacy Boundaries**: No live Mobilis GPS/ticketing feeds assumed; no camera frames stored locally or remotely; no personal user location histories stored on server (`MobilisTransit_DDM_Draft/main.tex` §1, §5.4; `main_changes7.tex` §1, §6; `apresentação.md` Part 3D).
  - **Accessibility**: Explicit labels, accessible reading order, system font scaling, and non-color-dependent status indicators (`MobilisTransit_DDM_Draft/main.tex` §5.2).
  - **Hardware**: Requires an ARCore-compatible Android phone (emulator permitted for non-AR UI) and a host machine running SUMO, Python backend/DB, and Ollama (`main_changes7.tex` §4.5; `MobilisTransit_DDM_Draft.pdf` §6.1).
- **Open Architectural Choices (for `ai-plan`)**:
  - **Python Backend Web Framework & Async Job Runner**: Concrete framework (e.g., FastAPI, Flask) and background task queue/process manager for running paired SUMO jobs asynchronously are not mandated.
  - **Backend Relational Database Engine**: A relational database is specified (`main_changes7.tex` §3.1, §4.2), but the specific engine (e.g., PostgreSQL vs. SQLite) remains open.
  - **Administration Web Frontend Technology**: Web forms and conversational chat UI are required (`main_changes7.tex` §3.3, §4.2), but the frontend stack (e.g., server-rendered templates, React, Vue, Streamlit) is open.
  - **Android UI, Persistence & Networking Libraries**: Jetpack Compose, MVVM + `StateFlow`, Coroutines, and Room over SQLite are explicitly proposed (`MobilisTransit_DDM_Draft/README.md`, `main.tex` §3) and adopted in later reports, while HTTP client library, serialization library, DI framework, and Android `minSdk` remain to be finalized after device compatibility checks.
  - **AR 3D/Panel Rendering Solution**: Choosing between native ARCore rendering (e.g., SceneView/Filament/Compose overlay) vs. an embedded Unity AR module for the 3D mini-route and Tabletop 3D full-route mode is explicitly deferred to device testing and `ai-plan` (`MobilisTransit_DDM_Draft/main.tex` §3.1; `main_changes7.tex` §3.2).
  - **Concrete Ollama Open-Weight Model & Fallback**: Exact tool-calling model weights (and hardware fallback strategy if SUMO + Ollama saturate RAM/CPU) remain open for benchmarking (`main_changes7.tex` §3.3, §6; `apresentação.md` Slide 12).
  - **Real-Time Update Transport / Demo Sync Strategy**: Standard REST polling starts at `5 s`, while live demonstrations target `< 2 s` display latency from server update to client rendering (`main_changes7.tex` §5.3, `DEC-003`); whether to satisfy this via a configurable faster demo polling interval (e.g., `≤ 1 s`) or an optional push/SSE/WebSocket channel on top of the REST snapshot contract is open for `ai-plan`.
  - **Exact REST/JSON Payload Schemas, Dataset Size & Traffic-Multiplier Bounds**: Endpoint paths are preliminary (`MobilisTransit_DDM_Draft/main.tex` §4); JSON schemas, dataset journey counts/scenario matrix, and safe numeric bounds for the traffic multiplier (`DEC-002`) are finalized during planning and pilot runs (`apresentação.md` Part 3A–3B).
  - **Latency Telemetry & Clock-Alignment Mechanism**: Implementation of aligned/offset-compensated timestamp collection across worker, API, and mobile client (`apresentação.md` Part 3B) is open for `ai-plan`.

## 6. Out of Scope & Future Work
- **Live Mobilis GPS Telemetry Ingestion & Operational Digital Twin**: Real-time operator GPS feeds, map-matching to road geometry, ticketing data integration, and field model re-validation (`tema.MD` §5, §8; `MobilisTransit_DDM_Draft/main.tex` §1; `REPORT_EIT_VAR_IEEE/main_changes7.tex` §1, §2.1, §4.2; `Apresentação/apresentação.md` Slide 5, Slide 12, Part 3C).
- **Multi-Line Network, Transfers & City-Wide Optimization**: Additional Mobilis routes beyond Line 9, inter-line transfers, city-wide schedule optimization, and deployment on physical buses or public street stops requiring municipal marker permits (`MobilisTransit_DDM_Draft/main.tex` §2 Priority Table; `REPORT_EIT_VAR_IEEE/main_changes7.tex` §4.1, §6).
- **Kalman Filter Online State Estimator**: Optional ML extension only if time permits after completing the primary AAP comparison (historical baseline, regularized linear regression, XGBoost) (`REPORT_EIT_VAR_IEEE/main_changes7.tex` §3.1; `Apresentação/apresentação.md` Slide 12, Part 3A, Part 3C).
- **Mobile Feature Extensions**: Approaching-bus push/local notifications, comparison result export, real-time user geolocation, and additional client-side synchronization optimizations (`MobilisTransit_DDM_Draft/main.tex` §2 Priority Table; `Apresentação/apresentação.md` Part 3C).
- **Advanced Agentic Analytical Queries**: Complex analytical workflows beyond the three core backend tools (`list_scenarios`, `run_delay_experiment`, `compare_experiments`) (`Apresentação/apresentação.md` Part 3C).
- **Generic Bus-Stop Sign Recognition**: Computer-vision recognition of arbitrary physical bus-stop signage without printed reference markers (`MobilisTransit_DDM_Draft/main.tex` §3.1; `REPORT_EIT_VAR_IEEE/main_changes7.tex` §3.2).
- **Virtual Reality (VR) Component & TEI Business Model**: Originally sketched in `tema.MD` (§6, §8) and omitted from `REPORT_EIT_VAR_IEEE/main_changes7.tex` and all subsequent specifications; confirmed dropped (`DEC-001`).
